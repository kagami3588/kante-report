# KAGAMI｜子どもの進路・自己理解支援アンケート 計測システム

「感想を集めるアンケート」ではなく、**自己理解 → 判断軸 → 進路の明確化 → 自己決定 → 行動 → 結果** の流れを
**鑑定直後と3ヶ月後の同じ意味の質問**で測り、KAGAMIの価値を客観データにするための Google Apps Script です。

| ファイル | 内容 |
|---|---|
| `Code.gs` | 本体。実行すると スプレッドシート＋4フォーム＋集計＋ダッシュボード＋グラフ を自動生成 |
| `appsscript.json` | マニフェスト（タイムゾーン Asia/Tokyo、V8）。任意 |

---

## STEP 1｜今回のアンケート設計の考え方

1. **満足度ではなく「変化」を測る**。「鑑定が当たっていたか」は聞きません。
2. 測定の流れは 7 領域：自己理解 → 判断軸 → 進路の明確さ → 自己決定・自信 → 将来への不安 → 行動 → 結果。
3. 領域1〜5は **鑑定直後と3ヶ月後で同じ意味の質問**（比較ペア S1〜S5, A1〜A4, C1〜C3, D1〜D3, N1）。差分＝変化量。
4. **全て4段階評価**（全くそう思わない／あまりそう思わない／まあそう思う／とてもそう思う）。中央選択肢なし、逆転項目なし、**数字が大きいほど良い**。
   「不安」は「不安は少ない」と聞くので、数字が大きい＝不安が少ない。
5. **行動（やったこと）と結果（進路状況）を別の質問**で取得。
6. **鑑定前の悩みは3ヶ月後に再質問しない**（既存の初回アンケートを `対象者管理` に転記して使う）。
7. 個人情報は取らない。紐づけは **対象者ID（KGM-0001 形式）** のみ。
8. 「鑑定がなかった場合と比べて」は反実仮想なので、**因果の証明ではなく本人・保護者の主観的な影響評価**として扱う。

## STEP 2｜4つのフォームの構成

| | フォーム | 質問数 | セクション |
|---|---|---|---|
| A | 鑑定直後｜お子様 | 22 | 基本情報／自己理解／判断軸／進路の明確さ／自己決定・将来／鑑定について |
| B | 鑑定直後｜保護者様 | 22 | 基本情報／お子様への理解／向き合い方／進路の明確さ／将来・親子関係／鑑定について |
| C | 3ヶ月後｜お子様 | 27 | 基本情報／自己理解／判断軸／進路の明確さ／自己決定／鑑定の活用／実際の行動／3ヶ月間の変化 |
| D | 3ヶ月後｜保護者様 | 28 | 基本情報／お子様への理解／向き合い方／進路の明確さ／親子関係／鑑定の活用／実際の変化 |

質問文・順序・選択肢は依頼内容のとおりです（`Code.gs` の `FORM_SPECS`）。セクションごとにページを分け、1画面に詰め込みません。

## STEP 3｜各質問で取得できるデータ

| 領域 | A / B | C / D | 取得データ |
|---|---|---|---|
| 自己理解 | Q3–7 | Q2–6 | 4段階×5（得意・苦手／環境／価値観／性格／合わない環境） |
| 判断軸 | Q8–11 | Q7–10 | 4段階×4 |
| 進路の明確さ | Q12–14 | Q11–13 | 4段階×3 |
| 自己決定・前向き | A:Q15,16,18 / B:Q15,16 | C:Q14,15,17 / D:Q14,15 | 4段階 |
| 不安（少なさ） | Q17 | C:Q16 / D:Q16 | 4段階×1 |
| 親子対話（補助） | B:Q18 | D:Q17 | 4段階（保護者のみ） |
| 鑑定の活用 | ― | C/D:Q18–20 | Q18＝鑑定活用率の対象 |
| 行動 | ― | Q21（4段階・専用選択肢）＋C:Q22/D:Q22（複数選択） | 行動率・継続行動率・行動内容 |
| 結果 | ― | C:Q23,24 / D:Q23 | 考えの変化／進路状況（6段階） |
| 鑑定の影響 | ― | C:Q25,26 / D:Q24–26 | 役に立った／鑑定影響（主観） |
| 納得・参考（補助） | Q19–21 | ― | 満足度だけで価値判断しないための参考値 |
| 自由記述（任意） | Q22 | C:Q27 / D:Q28 | ケーススタディ用の実際の言葉 |

全質問に「役割」を付与しており、スプレッドシートの `質問一覧` シートで確認できます。

> **保護者の「自己決定・前向き」は2項目**：お子様用の「自分は自分のままでいい」（Q18）に相当する保護者の質問が依頼内容に無いため、保護者は Q15・Q16 の平均です。
> 質問は勝手に追加していません。

## STEP 4｜スコアリング方法

| スコア | 対象 | 計算 |
|---|---|---|
| A 自己理解 | 5項目 | 平均 |
| B 判断軸 | 4項目 | 平均 |
| C 進路明確度 | 3項目 | 平均 |
| D 自己決定・前向き | 3項目（保護者は2項目） | 平均 |
| E 不安の少なさ | 1項目 | そのまま（大きい＝不安が少ない） |

- **変化量＝3ヶ月後 − 鑑定直後**（同じ対象者ID・両方回答した人のみ）
- **判定**：`+0.25以上 → 改善` ／ `−0.24〜+0.24 → 変化なし` ／ `−0.25以下 → 低下`（しきい値は `設定` シートで変更）
- **行動率**＝Q21 が 3 or 4 ／ **継続行動率**＝4 ／ **方向性決定率**＝進路状況が「候補がいくつか決まった」以上 ／ **具体的進路決定率**＝「具体的な進路を決めた」以上
- **鑑定活用率**＝Q18 が 3 or 4（子ども・保護者別）／ **鑑定影響率**＝「鑑定がなかった場合と比べ影響」が 3 or 4（※主観評価）
- 同一ID・同一フォームの重複回答は **最新の1件** を採用

## STEP 5｜3ヶ月後にどんな変化を分析できるか

- 5スコアの 直後→3ヶ月後（平均・変化量・改善/変化なし/低下の割合）— お子様／保護者別
- 行動率・継続行動率・方向性決定率・具体的進路決定率、進路状況の分布、行動内容の内訳
- 鑑定活用率・鑑定影響率・「役に立った」割合
- `クロス集計`（自動）
  - 分析A 自己理解の変化 × 行動率　／　分析B 判断軸の変化 × 進路決定率　／　分析C 進路明確度の変化 × 具体的進路決定率
  - 分析D 鑑定活用度 × 行動率　／　分析E 鑑定影響度 × 進路明確度の変化　／　分析F お子様 × 保護者
- `ケーススタディ`：ID別に「変化量・行動・進路結果・鑑定影響・実際の自由記述」を一覧（**ストーリーは自動生成しません**）
- 属性（学年区分・初回アンケートの悩みカテゴリ）を `対象者管理` に入れておけば、「どんな家庭に特に有効か」を後から切り出せます（`回答ログ`・`個人別分析` が分析用データ）

## STEP 7｜貼り付け方法

1. <https://script.google.com> → **新しいプロジェクト**

3. （任意）左の歯車 → 「`appsscript.json` マニフェスト ファイルをエディタで表示する」にチェック → `appsscript.json` の内容を貼り付け

## STEP 8｜初回実行方法

1. 関数選択で **`setupKagamiSystem`** → ▶ 実行
2. 承認画面で「権限を確認」→ Googleアカウント → 「詳細」→「（プロジェクト名）に移動」→ 許可
   （スプレッドシート・フォーム・トリガーの作成に必要）
3. 完了まで 1〜3 分。ログに `✅ 完了` とスプレッドシートURLが出ます。

**再実行しても複製されません**（作成物のIDを `PropertiesService` に保存）。

| 関数 | 用途 |
|---|---|
| `setupKagamiSystem()` | 初回構築。作成済みなら何もせず案内だけ表示 |
| `updateKagamiSystem()` | 既存システムの更新（シート・数式・グラフを再生成。回答は消えない） |
| `createNewKagamiSystem()` | あえて別システムを新規作成（旧IDは履歴に残る・旧ファイルは削除しない） |
| `issueSubjectIds()` | 対象者IDを発行（発行数は `設定` シート）＋事前入力URLを作成 |
| `showFormUrls()` | 4フォームのURLをログに表示 |

## STEP 9｜GoogleフォームのURL確認方法

- スプレッドシートの **`フォームURL`** シート（回答用URL／編集用URL）
- または `showFormUrls()` を実行して実行ログを見る
- 配布は **`対象者管理` の「事前入力URL」** を推奨（IDが自動入力され、入力ミスが防げます）。編集用URLは共有しないでください。

## STEP 10｜実際にテスト回答する方法

1. `issueSubjectIds()` を実行 → `対象者管理` に `KGM-0001`… が並ぶ
2. 「事前入力URL A」を開いて回答（Aを子ども用、Bを保護者用）
3. 「事前入力URL C / D」を開いて回答（テストでは直後より高めに答えると変化が見えます）
4. `ダッシュボード`／`個人別分析` を確認
5. テスト後は、回答シート（③〜⑥）の回答行と、フォームの回答（フォーム編集画面 → 回答 → 削除）を消してください。
   `回答ログ`・`個人別分析` は次回の再計算で自動的にクリアされます（`recalculateAll()` を実行）。

## STEP 11｜回答後にダッシュボードがどう更新されるか

回答送信 → インストーラブルトリガー `onKagamiFormSubmit` が `recalculateAll()` を実行：

1. 4つの回答シートを読み、スコア・行動・進路状況を計算
2. `回答ログ`（回答日時・対象者ID・回答者区分・アンケート種別つき）を再作成
3. `個人別分析` の入力列を更新 → 変化量・判定・親子差は **数式** で自動計算
4. `全体集計`・`クロス集計`・`ケーススタディ`・`ダッシュボード`（数式・グラフ）が自動で追従
5. `対象者管理` の回答状況（✓）も更新

数秒〜数十秒で反映されます。Nが `設定` の最小人数（既定30）未満の間は、ダッシュボードに「参考値」の警告が出ます。

## Google Forms の制約と、実装上の対応（省略せず明示）

| # | Google Formsの制約 | 問題点 | 採用した実装 | データへの影響 |
|---|---|---|---|---|
| 1 | フォームに「隠しフィールド／自動採番」が無い | 対象者IDを手入力すると誤入力で紐づかない | ID欄に形式検証（`KGM-0000` 半角）＋ **事前入力URL** を `対象者管理` に自動生成。未登録IDは `個人別分析` に「未登録（要確認）」と表示。全角・小文字・空白は自動正規化 | 影響なし（誤入力の検知が可能） |
| 2 | 回答シートに「回答者区分」「アンケート種別」列を自動追加できない（フォーム別シートになる） | 要件の取得項目を満たせない | フォーム別シート名で区別しつつ、**`回答ログ`**（回答日時／対象者ID／回答者区分／アンケート種別つきの縦持ち）を自動生成 | 影響なし。分析・BIは `回答ログ` を使う |
| 3 | 回答は選択肢の**文字列**で保存され数値にならない | 平均・差の計算ができない | スクリプトが選択肢の位置(1〜4)に変換して計算 | 選択肢の文言を変えるとCode.gsの定義と一致が必要（定義から生成するので同時に更新される） |
| 4 | 目盛りスケール(ScaleItem)は両端にしかラベルを付けられない | 4段階の各ラベルが見えず子どもが迷う | **ラジオボタン(単一選択)** で4つの文言を全表示 | 影響なし（スマホでも押しやすい） |
| 5 | 回答ごとの「最新1件」制御やID存在チェックはフォーム側でできない | 同じIDで再回答・誤IDが混入しうる | 集計側で「同一ID・同一フォームは最新1件」を採用。再回答は `回答ログ` に全件残る | 修正回答が上書き扱いになる |
| 6 | 回答があるフォームの質問を差し替えると既存データと列が不整合になる | 更新時にデータが壊れる | 回答が1件でもあるフォームは **質問の差し替えをスキップ**（タイトル等のみ更新） | 質問を変えたい場合は新システム作成（`createNewKagamiSystem`）を推奨 |
| 7 | スタンドアロンスクリプトではスプレッドシートにメニューを出せない | ID発行などを画面から押せない | Apps Script エディタから関数を実行（ID発行数は `設定` シートで指定） | 影響なし |
| 8 | A・B の Q2「あなたとの関係」は選択肢が1つ（お子様本人／保護者） | 常に同じ回答になる | 依頼内容どおり実装（回答区分の確認用） | 分析には使用しない |

## 実績として使うときの注意

「鑑定を受ければ進路が決まる」「必ず人生が変わる」などの断定は使わず、実データに基づく表現にしてください（ダッシュボード「5. 実績として使うときの表現例」に自動生成されます）。

- ○「鑑定後3ヶ月で○％の方が進路について具体的な行動を起こしました」
- ○「○％の方が、鑑定で整理した自分の特徴を進路選択の参考にしています」
- ○「鑑定後、自己理解スコアが平均○ポイント上昇しました」

人数が統計的に意味のある規模になるまでは「KAGAMIによって○○が起きた」と断定せず、**回答者の自己評価・感じた変化・報告された行動・報告された進路状況**として扱います。
